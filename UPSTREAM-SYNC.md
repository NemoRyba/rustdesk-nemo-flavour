## TIER 3 — evaluate / align with our roadmap
- **M2 (controller-auth):** upstream `91b13be` added `ControlledContext { conn_audit_ref }` to `rendezvous.proto` — functionally our M2 idea. **Reuse/extend it**, don't build a parallel field.
- **Proto field-number discipline — VERIFIED 2026-09-04, no collision:** upstream took `switch_code = 11` on `PunchHoleRequest`/`RequestRelay` (`5438d20`). We add **zero** Nemo fields to those two messages or to `PublicKey`/`SignedId` (client protos byte-identical to merge-base `9043c15`; client `PunchHoleRequest` tops at `socket_addr_v6 = 10`, `RequestRelay` at `control_permissions = 9`; server sub protos are older still: `version = 6` / `token = 8`). **Standing rule:** any future Nemo field on those messages uses **12+** (10 = upstream `controlled_context`, 11 = upstream `switch_code`), and must be added to the client AND server `rendezvous.proto` in lockstep with matching numbers — the two subs sit on different proto baselines.
- **S-D nonce fix:** mirror upstream `e1bdb06`'s `FORMAT_V1` version-byte + legacy-fallback shape for the cross-direction nonce negotiation. (`tcp.rs` is conflict-free upstream.)
- **Features (decided 2026-09-04):**
  - ❌ **id-whitelist w/ wildcards (`d6ea17006`) — SKIP.** Endpoint-local filter on the connecting peer's *self-reported, unsigned* ID (the commit says so itself). Our server-side RBAC (`user_allowed_target` in `nemo_integration.rs`, enforced at the punch by `nemo_user_connection_rejection` on the controller's authenticated session token) is strictly stronger and central; porting would reintroduce trust in a spoofable ID plus a `LOGIN_FAILURES` arity change in `connection.rs`. Its incidental `awaiting_2fa` stale-Auth2fa guard is a separate tiny hardening if ever wanted.
  - ✅ **cross-session clipboard sync (`f28ac38cc`) — PORTED AT SOURCE (not yet built), Sciter redesign.** Upstream relays inside one Flutter process via `sessions::get_sessions()`; every Sciter remote session is its own process, so instead the CLIENT owner marker (`dyn.com.rustdesk.owner`) now carries a random per-process instance id (`clipboard.rs` `CLIPBOARD_INSTANCE_ID`; byte 0 unchanged so host/older builds are unaffected) and a controller's clipboard watcher forwards content written by a *different* controller process when the per-user local option `allow-sync-clipboard-between-sessions` is `Y` (`ClipboardSide::is_from_other_session`, unit-tested). Existing gates stay (`is_text_required()` = clipboard+keyboard enabled, no view-only bypass because the receive side is untouched). Toggle: Settings → General → "Sync clipboard between sessions" (`index.tis` kind `local`, DE/EN strings). Off by default. **Post-review fixes (2026-09-04):** option read via `LocalConfig::get_option_from_file` so the toggle reaches session processes already open (each is its own process with a once-loaded config cache); file clipboards + the KDE clear-placeholder are written with a no-instance-id marker (`get_owner_data_no_sync`) so they are never relayed (matches upstream, which leaves the file clipboard alone); and a **pre-existing hole closed**: `proto::from_clipboard` now drops a peer-supplied `dyn.com.rustdesk.owner` Special — on X11/Wayland the first entry of a duplicated format wins, so a malicious controller could forge a `[0x00]` marker and get its content re-broadcast by the host/sibling watchers as if user-typed (Windows/macOS were last-wins, unaffected; the name check is ASCII-case-insensitive since Win32 format names are). Sibling-id compare looks at exactly the 8 id bytes (padding-tolerant; a truncated id counts as our own = never forwarded). Delta re-reviewed by 2 refuters: not refuted. Known divergences: a screenshot copied to the clipboard inside a session (`screenshot.rs`) is also synced (upstream only relays received clipboards — consistent with the tooltip); the key is not in `KEYS_LOCAL_SETTINGS`, so the Nemo policy sync cannot force it off (add it there if admins should).
  - monitor-restore/toolbar UX (Flutter-side → Sciter equivalents are separate work).
- **`5eed50961` config at-rest zero-nonce:** hard (our `config.rs` diverged with the `permanent_password` module); lower priority.

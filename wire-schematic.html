The short answer

Is the client–server verification the same from both sides?

Yes — the same code path, not merely a similar one.

A workstation proving itself to the server and a technician proving themselves to the server run secure_tcp → nemo_rendezvous_key_exchange → NemoClientAuth, and hbbs runs one set of checks for both. Same message, same fields, same signature context, same registry lookup. A packet capture of the two handshakes could not tell them apart.

What is identical

  • The signed server ephemeral, and the client verifying it against the pinned key
  • The client-chosen session key, sealed to that ephemeral
  • The device-key signature, and what it is bound to
  • hbbs’ three checks: signature, registry, peer-id binding
  • require_device_key refusing a client that has none

What differs — and it is not the verification

  • Lifetime. The workstation holds its connection open for life and re-announces every 15 s; the technician opens a fresh socket per connect and drops it.
  • Layer 2. Only the technician logs in against LDAP and carries a session token. An unattended workstation authenticates to the management API with a device-key signature — no user, no password.
  • A technician running the client normally — without --no-server — also keeps a registered connection, so the same laptop does case 1 and case 2 at once.
Who is who

Three roles, not three products

Client A and client B are roles taken per session, not properties of a machine: A is whoever starts the call and watches, B is whoever answers and is watched. Here A is always a technician on the internet and B always a CAD workstation on site — but nothing in the software enforces that.

The question

Is everything encrypted?

No — but the gaps are now specific, not structural.

Encrypted unconditionally at shipped defaults: rendezvous signalling, server pushes, the relay control frame, the relayed payload, LDAP, and the management API's login and policy poll. Nine things remain, ranked by what would actually hurt.
